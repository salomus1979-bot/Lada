# API сервиса записи «Лада»

Express + SQLite (`node:sqlite`), без внешних сервисов. Схема базы — [docs/db-schema.md](../docs/db-schema.md).

## Запуск

```bash
npm install
npm run seed      # демо-данные из прототипа; перезалить: npm run seed -- --reset
npm start         # http://localhost:3001 (порт меняется через PORT)
npm run smoke     # сквозная проверка на отдельной временной базе
```

Тестовые аккаунты после сида: `owner@lada.local`, `admin@lada.local`,
`client@lada.local`, пароль у всех `Lada12345`.

## Соглашения

| | |
|---|---|
| Формат | только JSON, и в ответах, и в ошибках |
| Ошибки | `{ "error": { "code", "message", "details"? } }` |
| Коды | `400` неверные данные, `401` нет авторизации, `403` не хватает прав, `404` нет объекта, `409` конфликт |
| Авторизация | HttpOnly-cookie `lada_session`; для curl/тестов — `Authorization: Bearer <session_token>` |
| Время | принимается и хранится в UTC (`2026-10-23T11:00:00Z`). В ответах моменты приходят объектом `{ at_utc, local_date, local_time, timezone }` — локальное время добавлено только для показа |
| Деньги | целые копейки в `*_kopecks`; `*_display` — отформатированная строка для показа |
| Данные | ответы собираются из перечисленных полей, строки БД целиком не отдаются; `password_hash` не покидает базу |
| Валидация | входные данные проверяются до обращения к базе |

## Как считается свободное время

Отдельной таблицы слотов нет — всё вычисляется на лету
(`api/src/lib/availability.js`):

1. Суммарная длительность выбранных услуг плюс буферы уборки.
2. Рабочее окно мастера на дату: исключения (отпуск, больничный, разовые
   часы) перекрывают регулярный недельный график, из окна вырезается перерыв.
3. Пересечение с часами работы студии; особые дни перекрывают обычные.
4. Локальные границы переводятся в UTC — отдельно для каждой даты,
   поэтому переход на летнее время не ломает расчёт.
5. Вычитаются активные записи, блокировки времени и действующие удержания
   других клиентов. Своё удержание владельцу не мешает.
6. По сетке `slot_step_min` от начала окна остаются только те начала,
   где визит целиком влезает в окно и не пересекает занятое.
7. Отбрасывается прошедшее время и всё за горизонтом записи.

Истёкшие удержания удаляются физически при каждом расчёте доступности и
перед созданием или переносом записи, так что слот освобождается сам.
Отдельный таймер в `server.js` лишь подчищает таблицу в простое.

Проверка слота и запись выполняются в одной транзакции `BEGIN IMMEDIATE`,
поэтому два клиента не могут занять один слот.

## Постоянные блокировки в сиде

Фикстуры для проверки расчёта слотов. Правила недельные, а `time_blocks`
хранит конкретные моменты, поэтому сид раскладывает каждое правило
в отдельные строки на весь горизонт записи (3 месяца).

| Мастер | Когда | Тип | Причина |
|---|---|---|---|
| Анна Ковалева | четверг, 13:00–14:00 | `break` | Обед |
| Марина Орлова | пятница, 15:00–17:00 | `time_off` | Личное время |
| Елена Смирнова | суббота, весь день | `time_off` | Выходной |

Суббота у Елены остаётся рабочей по графику — день закрывает именно
блокировка. Так проверяется, что расчёт вычитает блокировки из графика,
а не просто читает график.

## Защита от двойной записи

Три независимых уровня — каждый работает, даже если предыдущий обошли.

**1. Триггеры БД.** `appointments_no_overlap_insert` и
`appointments_no_overlap_update` в [db/schema.sql](db/schema.sql) запрещают
пересечение визитов одного мастера. Отдельный триггер на UPDATE нужен,
чтобы перенос времени и смена мастера тоже проверялись. Условие:
`NEW.starts < существующий.ends AND NEW.ends > существующий.starts` —
визиты встык (15:00–16:00 и 16:00–17:00) пересечением не считаются.
Учитываются только статусы `pending` и `confirmed`.

**2. `BEGIN IMMEDIATE`.** Транзакция в [lib/db.js](src/lib/db.js) берёт
блокировку на запись сразу, а не при первом изменяющем операторе, как
DEFERRED по умолчанию. Иначе между проверкой «слот свободен» и вставкой
успевает вклиниться другое соединение.

**3. Обработка в API.** Конфликт от прикладной проверки и от триггера
приводятся к одному ответу: `409`, понятное сообщение и список ближайших
свободных слотов этого мастера. Текст ошибки SQLite наружу не уходит.

```json
{
  "error": {
    "code": "conflict",
    "message": "Это время уже занято, выберите другое",
    "details": {
      "reason": "overlap",
      "nearest_slots": [
        { "at_utc": "2026-10-16T14:00:00Z", "local_date": "2026-10-16",
          "local_time": "17:00", "timezone": "Europe/Moscow" }
      ]
    }
  }
}
```

## Осознанное наложение (только администратор)

`POST /api/appointments` и `.../reschedule` принимают `is_override: true` —
визит ставится поверх занятого времени. Поле действует, только если запрос
прислал `admin` или `owner`; у клиента и мастера оно молча игнорируется,
и попытка упирается в обычный `409`.

Триггеры пропускают строку с `is_override = 1`, но подзапрос по ней **не**
фильтрует: наложенный визит сам дальше блокирует другие записи.

Признак описывает текущее размещение, а не историю. При переносе он
вычисляется заново: администратор может прислать его снова, у клиента он
сбрасывается в `0`. Иначе визит, однажды поставленный внахлёст, навсегда
остался бы невидимым для UPDATE-триггера.

`is_override` отдаётся только в представлениях для персонала.

## Запись за клиента (только администратор)

`POST /api/appointments` принимает `client_user_id` — визит оформляется на
указанный аккаунт, а не на того, кто прислал запрос. Поле действует, только
если запрос прислал `admin` или `owner`; у клиента и мастера оно молча
игнорируется, как и `is_override`, — запись создаётся на них самих.

Отдельного `POST /api/admin/appointments` нет намеренно. Создание записи —
это проверка мастера и услуг, расчёт длительности, транзакция
`BEGIN IMMEDIATE`, обработка конфликта с подсказками и последний рубеж в виде
триггера. Второй эндпоинт означал бы второй такой путь, который пришлось бы
держать в согласии с первым; разница между «за себя» и «за клиента» — это
одно поле, а не другой сценарий. Поле ведёт себя ровно как `is_override`,
и проверка роли так же живёт в роуте.

Записать можно только аккаунт с ролью `client`. Неизвестный id и аккаунт
персонала дают одинаковый `404` — существование чужого аккаунта API не
подтверждает. Клиента для записи ищут через `GET /api/admin/clients`.

Что меняется на этом пути:

| Проверка | Как ведёт себя |
|---|---|
| `max_active_appointments` | считается по клиенту визита, а не по оформителю, и действует: `409` с текстом лимита |
| `is_blocked` | проверяется у клиента визита, но только когда он записывается сам |
| `consent` | обязателен только при записи на себя |
| `hold_token` | вместе с `client_user_id` — `400`: удержаний в админском пути нет |
| Ответ | админское представление: данные клиента и `is_override`, без `can_cancel` и прочих правил владельца |

**Про блокировку.** Она закрывает самостоятельную онлайн-запись, и её текст
прямо отправляет клиента звонить администратору. Действуй она и на админском
пути, звонок перестал бы помогать: снять блокировку в API тогда было нечем —
она выставлялась только автоматически после неявок
(`POST /api/admin/appointments/:id/status`), и аккаунт остался бы без записи
совсем. Поэтому администратор может записать заблокированного клиента;
решение он принимает осознанно, как и с наложением.

> Основание этого решения изменилось: разблокировка появилась —
> `PATCH /api/admin/clients/:id` с `is_blocked: false`. Значит возможен и
> другой порядок: отказывать и на админском пути (`409`), а администратор
> сначала снимает блокировку и только потом записывает — тогда каждое
> послабление оставляло бы след в `is_blocked`. Поведение намеренно оставлено
> прежним: менять его без решения владельца студии не стали. Если менять —
> это одна строка, условие `if (!forClient && client.is_blocked === 1)` в
> `api/src/routes/appointments.js`, плюс проверки в `api/test/smoke.js`.

**Про согласие.** Согласие на обработку данных — свойство клиента, а не
оформителя: галочка, поставленная чужой рукой, ничего не подтверждает.
Записать можно только существующий аккаунт, а регистрация
(`POST /api/auth/register`) согласия уже требует — значит у клиента оно есть
и без этого поля. При записи на себя `consent: true` остаётся обязательным.
А вот при **создании** клиента администратором аккаунта ещё нет, и раньше
согласия взять было негде — там поле обязательно, см. «Создание клиента
администратором».

**Про удержания.** `slot_holds` привязаны к `user_id` того, кто взял слот, и
нужны, пока клиент оформляет визит сам. Администратор видит сетку и ставит
запись сразу, поэтому токен здесь не нужен, а присланный вместе с
`client_user_id` — ошибка входных данных: иначе непонятно, чьё удержание
имел в виду вызывающий. Удержание самого клиента визита при этом не мешает поставить
ему же эту запись, а чужие удержания слот держат как обычно.

Созданная так запись — обычная: клиент видит её в `GET /api/appointments`,
отменяет и переносит по тем же правилам (окно `cancel_window_hours`, лимит
`max_reschedules`), и при переносе клиентом `is_override` сбрасывается в `0`.

## Источник записи

`appointments.source` — как визит попал в студию: радиогруппа «Источник
записи» на странице 24. Значения: `phone`, `in_person`, `whatsapp` и
`online`; в ответах рядом приходит `source_label` для показа.

`POST /api/appointments` принимает поле только у персонала — третье поле с
такой схемой после `is_override` и `client_user_id`: у клиента и мастера оно
молча игнорируется.

**`online` извне не принимается вовсе** — присланное, оно даёт `400`. Это
отметка самого API о том, что клиент оформил визит сам, и если бы её можно
было проставить запросом, по колонке больше нельзя было бы отличить
самостоятельную запись от студийной. Поэтому `source = 'online'` —
достоверный признак, а не пересказ слов вызывающего.

| Кто создал запись | Что в `source` |
|---|---|
| клиент сам | `online` всегда, даже если прислал другое значение |
| персонал, поле указано | `phone`, `in_person` или `whatsapp` |
| персонал, поле не указано | `NULL` — источник не указан, а не придуман |
| запись старше колонки | `NULL` |

`NULL` разрешён намеренно: колонка досоздаётся в уже существующей базе
(`ADDED_COLUMNS` в [lib/db.js](src/lib/db.js)), и `NOT NULL DEFAULT 'online'`
задним числом приписал бы старым записям источник, которого никто не называл.

При переносе `source` **не** меняется — в отличие от `is_override`:
тот описывает текущее размещение и пересчитывается, а источник — это
происхождение записи, и перенос его не отменяет.

Поле отдаётся только в админском представлении. Клиенту он не нужен: он и
так знает, как записался, — это внутренний учёт студии.

## Создание клиента администратором

`POST /api/admin/clients` — «Добавить клиента» на странице 26 и «Новый
клиент» в форме записи на странице 24: человек позвонил, аккаунта у него нет,
а записать его нужно сейчас. Поля как у регистрации, кроме пароля: имя,
телефон, e-mail, `consent`.

**Пароль не задаётся, аккаунт остаётся без входа.** Это ровно статус «Без
аккаунта» со страницы 26 — в ответах он виден как `has_login: false`.
`users.password_hash` объявлен `NOT NULL`, поэтому туда идёт заглушка
`nologin$<random>`: схема не `scrypt`, и `verifyPassword` отказывает на первой
же проверке, какой бы пароль ни пришёл. Попытка войти даёт тот же `401` с тем
же текстом, что и неизвестный e-mail, — по ответу нельзя узнать, что у
аккаунта нет пароля.

Почему не два других варианта:

| Вариант | Почему нет |
|---|---|
| Случайный пароль, админ передаёт голосом | Пароль пришлось бы показать в ответе API и продиктовать по телефону. Он осел бы в логах и в истории браузера администратора, а клиент получил бы «свой» пароль, который знает ещё один человек |
| Таблица одноразовых токенов приглашения | Токен нужно чем-то доставить, а почты в проекте нет. Таблица, строки которой некому отправить, — механика без канала: ссылку всё равно диктовали бы голосом |

Доступ в кабинет клиент получает сам — через восстановление пароля по своему
e-mail (страницы 14 и 15). **Этих эндпоинтов в API пока нет**, и пока их нет,
созданный администратором аккаунт войти не может вовсе. Это осознанный
предел: такой аккаунт нужен, чтобы у визита был клиент с именем, телефоном и
историей, — а не чтобы выдать ему доступ в обход почты. Кнопка «Отправить
сброс пароля» со страниц 26 и 27 — это и есть следующий шаг.

**Про согласие.** `consent: true` обязателен. При записи за клиента поле не
требуется: аккаунт уже есть, а значит согласие дали при регистрации
(`POST /api/auth/register` его требует). Здесь аккаунта ещё нет, и раньше
согласия взять было негде — поэтому администратор подтверждает, что получил
его у человека. Галочка чужой рукой не заменяет согласие клиента, но
единственный, кто может его здесь засвидетельствовать, — тот, кто говорил с
человеком. Проверка остаётся воротами, а не записью: колонки под согласие в
контракте нет, и заводить её без решения владельца студии не стали. Если
студии нужно доказательство, а не ворота, следующий шаг — `consent_at_utc` в
`users`.

**Уникальность.** E-mail — логин, он уникален в масштабе всех ролей: занятый
даёт `409`. Телефон на уникальность **не** проверяется: один номер на семью —
обычное дело. Чтобы не создать дубль, администратор сначала ищет клиента
через `GET /api/admin/clients?q=`.

**Чего нельзя.** Клиента без e-mail создать нельзя: в контракте
`users.email` — `NOT NULL UNIQUE`, это логин. Для записи «только по телефону»
понадобилось бы разрешить `email IS NULL` и переделать вход — это правка
контракта, а не эндпоинта.

## Блокировка и разблокировка клиента

`PATCH /api/admin/clients/:id` — кнопка «Заблокировать» на страницах 26 и 27
и правка контактов из карточки клиента. Принимает любое подмножество полей
`name`, `phone`, `email`, `is_blocked`; пустое тело — `400`. Посторонние поля
в SET не попадают: роль, счётчик неявок и хеш пароля этим эндпоинтом не
меняются. Менять можно только аккаунт с ролью `client` — неизвестный id и
аккаунт персонала дают одинаковый `404`.

До этого эндпоинта снять блокировку было нечем: `is_blocked` выставлялся
только автоматически, когда счётчик неявок достигал
`salon_settings.no_show_block_threshold`.

**Счётчик неявок при разблокировке не сбрасывается.** Неявки — история
клиента, её видно в списке и в карточке (страницы 26 и 27), и стирать её
значило бы подделывать прошлое. Из этого следует поведение, о котором нужно
знать: автоблокировка вернётся на следующей же неявке, потому что условие
сравнивает накопленный счётчик с порогом. Снятая блокировка — прощение
текущей блокировки, а не обнуление счёта.

**Сессии клиента при блокировке не удаляются.** Блокировка закрывает
онлайн-запись, а не доступ к своим визитам: по действующей сессии клиент
по-прежнему видит записи и текст с просьбой позвонить, но создать новую
запись не может — `POST /api/appointments` проверяет признак у клиента визита.
Новый вход при этом закрыт: `POST /api/auth/login` отвечает `403`.
