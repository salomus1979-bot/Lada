# Карта экранов «Лада»

Роль **клиент** (и гость): лендинг, авторизация, воронка записи, личный
кабинет, профиль, уведомления и служебные страницы — разделы ниже. Роль
**администратор** (и владелец): экраны 21–34 — в разделе
[«Административные экраны»](#административные-экраны-2134) в конце карты.
Экраны мастера (35–42) в карту не входят — они будут отдельно.

Источники: файлы прототипа в корне проекта, [Инвентаризация страниц.md](../Инвентаризация%20страниц.md),
роуты в [api/src/routes](../api/src/routes).

**Что из этой карты уже собрано.** Все клиентские экраны свёрстаны и лежат в
`web/pages` — список страниц и чем каждая наполняется см. в
[web/README.md](../web/README.md). Решения из раздела
[«Решения по расхождениям»](#решения-по-расхождениям) применены в вёрстке:
где данных не хватило, элемент убран, а на экране сказано почему.
Административные экраны (21–34) — каркас без данных, их очередь следующая.

**Про переходы.** Инвентаризация описывает прототип на 16.10.2026, когда ни одного
рабочего перехода в нём не было. Сейчас переходы работают на всех клиентских
экранах: в воронке и кабинете — через `window.location.href`, в авторизации и на
служебных страницах — обычными `<a href>`. В таблицах ниже указано фактическое
состояние кода на 18.10.2026.

Навигацию на экранах 13, 14, 15 и `System 01/02/03` доделали в этой правке — что
именно добавлено, перечислено в разделе [«Что добавлено в переходы»](#что-добавлено-в-переходы).
Пометка «по смыслу» осталась только там, где вести переход некуда: нужной
страницы в прототипе не существует.

**Про эндпоинты.** Колонка «Данные» — то, чем экран наполняется при открытии;
колонка «Действия» — то, что вызывают его кнопки. Там, где эндпоинта нет, стоит
«—» и экран попадает в список [пробелов в API](#экраны-которым-не-хватает-данных-в-api)
(у административных экранов [свой список](#административные-экраны-которым-не-хватает-данных-в-api)).
Базовый префикс у всех путей — `/api`.

## Экраны, которым не хватает данных в API

1. **`17. Кабинет - Уведомления`** — целиком без основы: в схеме нет таблицы уведомлений, в API нет ни одного роута. Нужны список с группировкой по дате, признак непрочитанного, отметка одного уведомления и «отметить все». Пока это единственный клиентский экран, у которого нет ни одного источника данных.
2. **Счётчик непрочитанных** — бейдж «2» на колокольчике и в сайдбаре экранов 7, 8, 9, 11, 16, 17. Следствие п. 1.
3. **`16. Кабинет - Профиль`** — читать профиль можно (`GET /auth/me`), менять нечем. Нет: обновления личных данных (имя, телефон, **дата рождения** — такого поля нет и в таблице `users`), смены пароля, переключателей уведомлений, загрузки фото, удаления аккаунта. Из четырёх блоков экрана API закрывает только «Активные сессии».
4. **`14. Восстановление пароля` и `15. Новый пароль`** — нет ни запроса ссылки, ни установки пароля по токену, ни таблицы для токенов сброса. Оба экрана не подключить вообще.
5. **`11. Кабинет - История записей`** — `GET /appointments` принимает только `scope` и `limit`. Нет фильтров по периоду, мастеру и услуге, нет `offset` под пагинацию, нет общего количества записей. Три фильтра и пагинация на экране не обеспечены.
6. **`7. Кабинет - Предстоящие`, табы** — «Прошедшие» и «Отменённые» на экране разделены, а `scope=past` отдаёт их одним списком: отдельного `scope=cancelled` нет. Либо делить на клиенте по `status`, либо добавлять scope.
7. **`9. Детали записи`, ссылка «Профиль мастера →»** — `GET /masters` отдаёт только список; эндпоинта одного мастера нет, публичной страницы профиля мастера нет и в прототипе.
8. **Воронка записи, удержание слота** — API держит слот (`POST /holds`, `hold_ttl_min`, `GET /holds/current`), но ни на шаге 3, ни на шаге 4 нет ни таймера, ни упоминания, что время зарезервировано. Экран под механику есть, самой механики на экранах нет.
9. **`Лада - Лендинг`, секция отзывов** — ни таблицы, ни эндпоинта отзывов. Тексты и имена захардкожены; формы отзыва в проекте тоже нет.
10. **`Лада - Лендинг`, виджет быстрой записи** — слоты в виджете показываются до выбора услуг, а `GET /masters/:id/availability` требует `service_ids` (длительность визита считается по услугам). Виджет либо наполняется выбранной по умолчанию услугой, либо остаётся витриной.
11. **`5. Запись создана`, «Добавить в календарь»** — нет выдачи `.ics`.
12. **`13. Регистрация`, индикатор силы пароля** — требования к паролю живут в валидаторе на сервере, отдельного эндпоинта с правилами нет; индикатор придётся дублировать на клиенте.
13. **`System 01 - Правила отмены`** — данные есть (`GET /settings`), но страница их не запрашивает: цифры в тексте зашиты. Не пробел в API, а несвязанный экран.
14. **Режим работы студии** — колонка «Режим работы» в подвале лендинга (`Лада - Лендинг`, `18. Каталог услуг`) и строка контактов на `9. Детали записи`. Часы лежат в таблице `salon_hours`, но `GET /settings` их не отдавал, а в разметке стояло «Ежедневно 10:00–21:00» — режим, которого у студии нет (на самом деле вт–сб, 10:00–20:00). Найдено при вёрстке лендинга.
15. **`12. Вход`, «Запомнить меня»** — `POST /auth/login` принимает только `email` и `password`; срок жизни сессии задан на сервере и из запроса не меняется. Галочке нечем управлять. Найдено при вёрстке экрана входа.
16. **`2. Запись - Шаг 2`, «Любой свободный мастер»** — карточка есть на экране, но в API такого режима нет: и `GET /masters/:id/availability`, и `POST /appointments` требуют конкретного `master_id`. Найдено при вёрстке шага 2.
17. **`3. Запись - Шаг 3`, удержание слота для гостя** — `POST /holds` требует сессию (`requireAuth`), а шаг 3 по прототипу проходится и без входа: войти предлагают только на шаге 4. Значит, у гостя выбранное время не держится ничем, и к моменту входа слот может уйти. Найдено при вёрстке шага 3.
18. **`3. Запись - Шаг 3`, точки «много/мало свободных окон» в календаре** — доступность считается на одну дату (`?date=`), эндпоинта «сколько окон в каждый день месяца» нет. Заполненность клеток — это 31 запрос на месяц, а в режиме «любой свободный мастер» втрое больше. Найдено при вёрстке шага 3.
19. **`3. Запись - Шаг 3` и `6. Ошибка - время занято`, состояния слотов** — в прототипе слот бывает «занят», «прошедший» и «заблокирован», а `GET /masters/:id/availability` отдаёт только свободное начало визита: занятого времени в ответе нет вовсе. Найдено при вёрстке шага 3.

## Решения по расхождениям

Правило, по которому принимались решения: **бэкенд сейчас не трогаем**, всё
закрывается на стороне экрана. Нумерация — по спискам выше.

### Экраны, которым не хватает данных

| № | Находка | Решение | Почему |
|---|---|---|---|
| 1 | `17. Уведомления` — лента | Собрать из существующих эндпоинтов | `GET /appointments?scope=all` даёт всё содержимое ленты: подтверждение визита, перенос (`reschedule_count`), отмену студией (`status` + `cancel_reason`), напоминание о ближайшем |
| 2 | Счётчик непрочитанных | — см. [список ниже](#чего-на-стороне-экрана-решить-нельзя) | Непрочитанность надо где-то хранить между заходами; на экране её не вычислить |
| 3 | `16. Профиль` — всё, кроме «Активных сессий» | Убрать элементы из вёрстки | Решено не открывать ради них бэкенд: экран верстается только блоком «Активные сессии» (`GET /auth/sessions` + `DELETE /auth/sessions/:id`), остальное менять нечем — подробности в списке ниже |

| 6 | `7` — табы «Прошедшие»/«Отменённые» | Данные в API есть: `GET /appointments?scope=past` | Ответ содержит оба вида, у каждой записи есть `status` — по нему табы и делятся |

| 8 | Воронка — таймер удержания слота | Данные в API есть: ответ `POST /holds` | Он возвращает `expires_in_sec` и `expires_at_utc` — таймер на шагах 3 и 4 заводится прямо от него |
| 9 | Лендинг — секция отзывов | Это не данные, а обычный контент страницы | Отзывы на лендинге — витрина, а не сущность сервиса: ни таблицы, ни формы отзыва в проекте не предполагалось |
| 10 | Лендинг — виджет быстрой записи | Собрать из существующих эндпоинтов | `GET /services` → берём услугу по умолчанию → `GET /masters?service_ids=…` → `GET /masters/:id/availability?date=сегодня&service_ids=…` |

| 12 | `13. Регистрация` — индикатор силы пароля | Это не данные, а обычный контент страницы | Правило постоянное (от 8 символов, буквы и цифры), и подпись на экране ему уже соответствует |
| 13 | `System 01` — правила отмены | Значение брать из API, текст привести к нему | `GET /settings` отдаёт `cancel_window_hours`, `max_reschedules`, `booking_horizon_months`, а «4 часа» и «два раза» в тексте — зашитые копии |

| 16 | `2. Запись - Шаг 2` — «Любой свободный мастер» | Собрать из существующих эндпоинтов на шаге 3 | Шаг 2 запоминает выбор как «любой», а шаг 3 спрашивает `GET /masters/:id/availability` у каждого подходящего мастера и объединяет слоты; при подтверждении в `POST /appointments` уходит мастер выбранного слота |
| 17 | Шаг 3 — удержание слота для гостя | Сказать об этом на экране | Гостю удержать слот нечем, и притворяться, что время за ним закреплено, нельзя: выбор сохраняется, а рядом стоит строка «без входа время не держится за вами» со ссылкой на вход. | 19 | Шаги 3 и 6 — состояния слотов «занят», «прошедший», «заблокирован» | Убрать элементы из вёрстки | В ответе доступности их нет: сервер отдаёт только то, на что можно записаться. ### Эндпоинты без экрана

| Эндпоинт | Решение | Почему |
|---|---|---|
| `GET /holds/current` | Оставить как есть | Шаг 4 вызовет его при открытии, чтобы восстановить таймер после перезагрузки; отдельного элемента для этого не нужно |
| `DELETE /holds/:token` | Добавить окно подтверждения | На «Выйти» в шагах 1–4 — подтверждение выхода из записи, по нему и снимается удержание |
| `GET /appointments?scope=all` | Оставить как есть | Экран у него появляется сам: из этого ответа строится лента уведомлений (п. 1) |
| `GET /services?master_id=<id>` | Экран будем верстать позже | Это фильтр для страницы мастера, которой в прототипе нет (п. 7) |
| `GET /health` | Оставить как есть | Служебная проверка живости, экран ей не нужен |
| `GET /settings` | Оставить как есть | Экраны-потребители есть (лендинг, воронка, `System 01`) — их нужно просто подключить, см. п. 13 |

### Чего на стороне экрана решить нельзя

- **Уведомления:** хранение признака «прочитано», действие «отметить все как
  прочитанные» и счётчик непрочитанных на колокольчике и в сайдбаре (пп. 1, 2).
- **Профиль:** сохранение личных данных, смена пароля, переключатели
  уведомлений, загрузка фото, удаление аккаунта (п. 3). **Решено:** бэкенд ради
  них не открываем, эти блоки из вёрстки убираются — экран `16` верстается
  только с «Активными сессиями». Поле «Дата рождения» убирается в любом случае:
  его нет и в таблице `users`.
- **Восстановление пароля:** экраны `14` и `15` целиком — запрос ссылки и
  установка нового пароля по токену (п. 4).
- **История записей:** выдача больше 100 записей — у `GET /appointments`
  потолок `limit` равен 100, клиентская пагинация дальше него не идёт (п. 5).

## Административные экраны, которым не хватает данных в API

1. **`34. Запросы мастеров`** — целиком без основы: в схеме нет таблицы
   запросов, в API нет ни одного роута. Нужны список запросов, тип (отмена
   визита, изменение карточки мастера), причина мастера, решение с автором и
   временем, разделение на новые и обработанные. Единственный административный
   экран без единого источника данных — как `17. Уведомления` у клиента.
2. **Бейдж «2» на пункте «Запросы»** — в сайдбаре всех 14 экранов. Следствие
   п. 1.
3. **`33. Настройки студии`** — читать можно почти всё (`GET /settings`),
   менять нечем: эндпоинта записи настроек в API нет. Не отдаются и два поля,
   которые экран показывает: `max_active_appointments` и
   `no_show_block_threshold` (в таблице `salon_settings` они есть). «Метро» нет
   ни в ответе, ни в таблице. Особые дни лежат в `salon_day_overrides`, но
   наружу не выходят ни на чтение, ни на запись. Единственный экран админки, где
   не обеспечено ни одно действие.
4. ~~**`22. Сетка расписания`, блоки «Перерыв»**~~ — **закрыто 22.10.2026.**
   Появился `GET /api/admin/time-blocks?date=&master_id=`: администратор видит
   заблокированное время всех мастеров за день — перерывы, выходные, отпуска
   и больничные. Ставить и снимать их он умел и раньше.
5. **`22`, таб «Неделя»** — и записи, и доступность админ запрашивает по одному
   дню. Недельной сводки для него нет (у мастера есть `GET /master/week`):
   неделя — это семь запросов.
6. **`27. Карточка клиента`, история визитов** — у `GET /admin/appointments` нет
   фильтра по клиенту, и собрать записи одного человека нечем. Таблица «Дата /
   Мастер / Услуги / Сумма / Статус» и блок «Ближайшая запись» не обеспечены.
7. **`27`, один клиент** — эндпоинта одного клиента нет: карточку приходится
   наполнять строкой из `GET /admin/clients?q=`.
8. **`27`, метрики и бейдж** — «Отмен», «Средний чек», «Первый визит», «Сумма за
   всё время» и бейдж «Постоянный клиент» в `clientAdminView` не входят. Из
   шести метрик экрана API закрывает две: «Визитов» и «Неявок».
9. **Заметки о клиенте** — `27` (блок «Заметки», поле «Добавить заметку»,
   пометка «Заметки видят мастера и администраторы») и `25` («Внутренняя
   заметка · клиент не видит»): ни таблицы, ни роутов.
10. ~~**`25. Детали записи`, журнал изменений**~~ — **закрыто 22.10.2026.**
    Появилась таблица `appointment_events`: кто создал, кто перенёс откуда и
    куда, кто отменил и почему, кто сменил статус. История приходит в поле
    `history` у `GET /appointments/:id` и у списка `GET /admin/appointments`.
11. **`25`, «Изменить состав услуг» и «Сменить мастера»** — перенос меняет
    только время; состав услуг и мастера после создания записи не меняет ничто.
12. **`23. Записи`, фильтры, поиск и экспорт** — эндпоинт принимает `date_from`,
    `date_to`, `master_id`, `status`, `limit`, `offset`; фильтра по услуге и
    поиска по клиенту или телефону нет. Выдачи файла под «Экспорт» тоже нет —
    на экране кнопка отключена.
13. **`23`, массовая отмена** — «Отменить выбранные» и «Выбрано 3» требуют
    пакетной операции, а отмена в API одна на запись.
14. **`26. Клиенты`, фильтры** — `?status=active|blocked` есть, фильтров
    «Последний визит: год» и «Мастер» нет.
15. **Сброс пароля** — «Отправить сброс пароля» на `26`, `27` и `29`: роутов
    восстановления пароля в API нет вовсе. Та же нехватка, что у клиентских
    экранов `14` и `15` (п. 4 клиентского списка).
16. **`24. Новая запись`, приглашение клиенту** — «Отправить приглашение на
    e-mail» нечем: ни отправки писем, ни таблицы приглашений. Клиент, созданный
    администратором, остаётся без пароля (`has_login: false`, статус «Без
    аккаунта» на `26`).
17. **`28. Мастера`, рейтинг** — звёзды и «4,9» на карточках, «Рейтинг» в
    статистике `29`: ни таблицы оценок, ни эндпоинта. Та же нехватка, что у
    отзывов на лендинге (п. 9 клиентского списка).
18. **`28`/`29`, доступ в систему** — «Выдать доступ», «Отозвать доступ»,
    «Последний вход»: колонка `masters.user_id` в схеме есть, и `GET
    /admin/masters` отдаёт по ней `access`, но связать аккаунт с карточкой
    мастера или разорвать связь API не умеет. Создания аккаунта мастера тоже
    нет: публичная регистрация выдаёт только роль `client`.
19. ~~**`28`, возврат из архива**~~ — **закрыто 22.10.2026.** `PATCH`
    принимает `is_active`, поэтому отключённого мастера (и услугу) можно
    вернуть в работу тем же переключателем, которым их отключают. Тогда же
    изменилось и удаление: решает его сервер — строку без ссылок он удаляет
    из базы, строку с записями отключает и объясняет, почему.
20. **`29`, загрузка фото** — API принимает только `photo_url` строкой; роута
    загрузки файла нет (папка `uploads/` в корне — не часть сервиса).
21. **`29`, модерация изменений мастера** — «1 изменение ждёт проверки»,
    «Было / Стало»: мастер свою карточку и не меняет (`GET /master/me` только
    на чтение), очереди изменений в API нет.
22. **`31. Услуги`, категории и поиск** — кнопка «Категории»: категории только
    читаются (`GET /service-categories`), создания, правки и сортировки нет.
    Поиска по услугам в `GET /admin/services` тоже нет.
23. **`32. Услуга (форма)`, мастера услуги** — чекбоксы «Выполняют мастера»
    сохраняются только через `PATCH /admin/masters/:id` по каждому мастеру:
    обратной связки «задать мастеров услуге» одним запросом в API нет.
24. **`32`, шаг длительности** — на экране «Шаг 10 минут», в API длительность
    кратна 5 (`duration_min % 5`). Расхождение в пользу API: экран строже, чем
    сервер.
25. **`21. Дашборд`, метрики** — «Загрузка»: `load_percent` считает только
    `GET /master/week` и только для себя, администратору он закрыт. «Новых
    клиентов»: `created_at_utc` в строках есть, фильтра по дате создания и
    счётчика нет. «Свободных окон»: доступность считается на одного мастера и
    одну дату за запрос, причём `service_ids` обязательны. «Отмен сегодня»
    считается только как «визиты на сегодня со статусом отмены»: фильтра по
    `cancelled_at_utc` нет, и отмену сегодняшнего дня по будущей записи
    метрика не увидит.
26. **`21`, блок «Требует внимания»** — «Клиент не пришёл» и «Пустое
    расписание» собираются из записей и графика, а «Запрос на отмену» — нет
    (п. 1). Из трёх карточек блока обеспечены две.
27. **Выход из админки** — «Выйти» в сайдбаре всех 14 экранов ведёт ссылкой на
    лендинг, `POST /auth/logout` не вызывается. Не пробел в API, а несвязанная
    кнопка — как `GET /settings` на `System 01` (п. 13 клиентского списка).

## Административные эндпоинты без экрана

Перечислены роуты `/api/admin/*` и те общие роуты, которые открыты персоналу,
но на административных экранах не вызываются.

| Эндпоинт | Почему без экрана |
|---|---|
| `POST /api/admin/clients` | Экраны-потребители есть (`24` — «Новый клиент», `26` — «Добавить клиента»), а формы с полями имени, телефона, e-mail и согласия в прототипе нет: обе кнопки ведут на экран записи. Не хватает экрана, а не данных |
| `PATCH /api/admin/clients/:id` (`name`, `phone`, `email`) | Из четырёх полей эндпоинта экраны используют одно — `is_blocked` («Заблокировать» на `26` и `27`). Правки контактов нет ни на одном экране: на `27` имя, телефон и e-mail показаны текстом |
| `POST /api/appointments/:id/reschedule` (персоналом) | Админского экрана выбора нового времени нет: «Перенести» на `22`, `25` и `34` ведёт на детали записи. Перенос за клиента без окна и лимита API умеет, вызвать его неоткуда |
| `POST /api/admin/masters/:id/time-blocks`, `DELETE /api/admin/masters/:id/time-blocks/:blockId` | Точечная блокировка времени есть только в кабинете мастера (`39`). На `30` администратор заводит исключения графика, а не блокировки; в сетке `22` они видны, но ставить и снимать их оттуда нечем |
| `DELETE /api/admin/masters/:id/exceptions/:exceptionId` | Элемент на экране `30` есть — иконка корзины у исключения, — но она без обработчика |
