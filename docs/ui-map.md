# Карта клиентских экранов «Лада»

Только роль **клиент** (и гость): лендинг, авторизация, воронка записи, личный
кабинет, профиль, уведомления и служебные страницы. Экраны мастера (35–42) и
администратора (21–34) в карту не входят — они будут отдельно.

Источники: файлы прототипа в корне проекта, [Инвентаризация страниц.md](../Инвентаризация%20страниц.md),
роуты в [api/src/routes](../api/src/routes).

**Про переходы.** Инвентаризация описывает прототип на 16.10.2026, когда ни одного
рабочего перехода в нём не было. Сейчас переходы работают на всех клиентских
экранах: в воронке и кабинете — через `window.location.href`, в авторизации и на
служебных страницах — обычными `<a href>`. В таблицах ниже указано фактическое
состояние кода на 18.10.2026.

Навигацию на экранах 13, 14, 15 и `System 01/02/03` доделали в этой правке — что
именно добавлено, перечислено в разделе [«Что добавлено в переходы»](#что-добавлено-в-переходы).
Пометка «по смыслу» осталась только там, где вести переход некуда: нужной
страницы в прототипе не существует.

**Про эндпоинты.** Колонка «Данные» — то, чем экран наполняется при открытии;
колонка «Действия» — то, что вызывают его кнопки. Там, где эндпоинта нет, стоит
«—» и экран попадает в список [пробелов в API](#экраны-которым-не-хватает-данных-в-api).
Базовый префикс у всех путей — `/api`.

## Экраны, которым не хватает данных в API

1. **`17. Кабинет - Уведомления`** — целиком без основы: в схеме нет таблицы уведомлений, в API нет ни одного роута. Нужны список с группировкой по дате, признак непрочитанного, отметка одного уведомления и «отметить все». Пока это единственный клиентский экран, у которого нет ни одного источника данных.
2. **Счётчик непрочитанных** — бейдж «2» на колокольчике и в сайдбаре экранов 7, 8, 9, 11, 16, 17. Следствие п. 1.
3. **`16. Кабинет - Профиль`** — читать профиль можно (`GET /auth/me`), менять нечем. Нет: обновления личных данных (имя, телефон, **дата рождения** — такого поля нет и в таблице `users`), смены пароля, переключателей уведомлений, загрузки фото, удаления аккаунта. Из четырёх блоков экрана API закрывает только «Активные сессии».
4. **`14. Восстановление пароля` и `15. Новый пароль`** — нет ни запроса ссылки, ни установки пароля по токену, ни таблицы для токенов сброса. Оба экрана не подключить вообще.
5. **`11. Кабинет - История записей`** — `GET /appointments` принимает только `scope` и `limit`. Нет фильтров по периоду, мастеру и услуге, нет `offset` под пагинацию, нет общего количества записей. Три фильтра и пагинация на экране не обеспечены.
6. **`7. Кабинет - Предстоящие`, табы** — «Прошедшие» и «Отменённые» на экране разделены, а `scope=past` отдаёт их одним списком: отдельного `scope=cancelled` нет. Либо делить на клиенте по `status`, либо добавлять scope.
7. **`9. Детали записи`, ссылка «Профиль мастера →»** — `GET /masters` отдаёт только список; эндпоинта одного мастера нет, публичной страницы профиля мастера нет и в прототипе.
8. **Воронка записи, удержание слота** — API держит слот (`POST /holds`, `hold_ttl_min`, `GET /holds/current`), но ни на шаге 3, ни на шаге 4 нет ни таймера, ни упоминания, что время зарезервировано. Экран под механику есть, самой механики на экранах нет.
9. **`Лада - Лендинг`, секция отзывов** — ни таблицы, ни эндпоинта отзывов. Тексты и имена захардкожены; формы отзыва в проекте тоже нет.
10. **`Лада - Лендинг`, виджет быстрой записи** — слоты в виджете показываются до выбора услуг, а `GET /masters/:id/availability` требует `service_ids` (длительность визита считается по услугам). Виджет либо наполняется выбранной по умолчанию услугой, либо остаётся витриной.
11. **`5. Запись создана`, «Добавить в календарь»** — нет выдачи `.ics`.
12. **`13. Регистрация`, индикатор силы пароля** — требования к паролю живут в валидаторе на сервере, отдельного эндпоинта с правилами нет; индикатор придётся дублировать на клиенте.
13. **`System 01 - Правила отмены`** — данные есть (`GET /settings`), но страница их не запрашивает: цифры в тексте зашиты. Не пробел в API, а несвязанный экран.

## Эндпоинты без экрана

Перечислены только клиентские роуты. Админские (`/api/admin/*`) и мастерские
(`/api/master/*`) не рассматривались — их экраны вне этой карты.

| Эндпоинт | Почему без экрана |
|---|---|
| `GET /holds/current` | Нет экрана и нет элемента, который показывал бы действующее удержание или остаток времени по нему (см. п. 8 выше) |
| `DELETE /holds/:token` | Снять удержание нечем: кнопки «Выйти» на шагах 1–4 ничего не вызывают, подтверждения выхода из воронки в прототипе нет |
| `GET /appointments?scope=all` | Ни один экран не показывает все записи разом: 7 — только предстоящие, 11 — только прошедшие |
| `GET /services?master_id=<id>` | Фильтр «услуги конкретного мастера» — экрана с витриной одного мастера нет (как и публичного профиля мастера, п. 7) |
| `GET /health` | Служебный; ближайший кандидат — `System 03`, но она его не вызывает |
| `GET /settings` | Формально есть кому отдавать (лендинг, воронка, `System 01`), но ни один экран прототипа его не использует — все значения зашиты в разметку |

## Решения по расхождениям

Правило, по которому принимались решения: **бэкенд сейчас не трогаем**, всё
закрывается на стороне экрана. Нумерация — по спискам выше.

### Экраны, которым не хватает данных

| № | Находка | Решение | Почему |
|---|---|---|---|
| 1 | `17. Уведомления` — лента | Собрать из существующих эндпоинтов | `GET /appointments?scope=all` даёт всё содержимое ленты: подтверждение визита, перенос (`reschedule_count`), отмену студией (`status` + `cancel_reason`), напоминание о ближайшем |
| 2 | Счётчик непрочитанных | — см. [список ниже](#чего-на-стороне-экрана-решить-нельзя) | Непрочитанность надо где-то хранить между заходами; на экране её не вычислить |
| 3 | `16. Профиль` — всё, кроме «Активных сессий» | Убрать элементы из вёрстки | Решено не открывать ради них бэкенд: экран верстается только блоком «Активные сессии» (`GET /auth/sessions` + `DELETE /auth/sessions/:id`), остальное менять нечем — подробности в списке ниже |
| 4 | `14`/`15` — восстановление пароля | — см. [список ниже](#чего-на-стороне-экрана-решить-нельзя) | Роутов сброса пароля нет вообще, собрать их из существующих нечем |
| 5 | `11. История` — фильтры и пагинация | Собрать из существующих эндпоинтов | `GET /appointments?scope=past&limit=100` отдаёт полные записи с мастером, услугами и датами — период, мастер, услуга и страницы считаются на клиенте |
| 6 | `7` — табы «Прошедшие»/«Отменённые» | Данные в API есть: `GET /appointments?scope=past` | Ответ содержит оба вида, у каждой записи есть `status` — по нему табы и делятся |
| 7 | `9` — ссылка «Профиль мастера →» | Убрать элемент из вёрстки | Страницы мастера в прототипе нет; данные для неё в `GET /masters` уже полные, вернуть ссылку можно вместе с экраном |
| 8 | Воронка — таймер удержания слота | Данные в API есть: ответ `POST /holds` | Он возвращает `expires_in_sec` и `expires_at_utc` — таймер на шагах 3 и 4 заводится прямо от него |
| 9 | Лендинг — секция отзывов | Это не данные, а обычный контент страницы | Отзывы на лендинге — витрина, а не сущность сервиса: ни таблицы, ни формы отзыва в проекте не предполагалось |
| 10 | Лендинг — виджет быстрой записи | Собрать из существующих эндпоинтов | `GET /services` → берём услугу по умолчанию → `GET /masters?service_ids=…` → `GET /masters/:id/availability?date=сегодня&service_ids=…` |
| 11 | `5. Запись создана` — «Добавить в календарь» | Собрать из существующих эндпоинтов | `GET /appointments/:id` даёт начало, конец, мастера и состав услуг — файл `.ics` собирается в браузере |
| 12 | `13. Регистрация` — индикатор силы пароля | Это не данные, а обычный контент страницы | Правило постоянное (от 8 символов, буквы и цифры), и подпись на экране ему уже соответствует |
| 13 | `System 01` — правила отмены | Значение брать из API, текст привести к нему | `GET /settings` отдаёт `cancel_window_hours`, `max_reschedules`, `booking_horizon_months`, а «4 часа» и «два раза» в тексте — зашитые копии |

### Эндпоинты без экрана

| Эндпоинт | Решение | Почему |
|---|---|---|
| `GET /holds/current` | Оставить как есть | Шаг 4 вызовет его при открытии, чтобы восстановить таймер после перезагрузки; отдельного элемента для этого не нужно |
| `DELETE /holds/:token` | Добавить окно подтверждения | На «Выйти» в шагах 1–4 — подтверждение выхода из записи, по нему и снимается удержание |
| `GET /appointments?scope=all` | Оставить как есть | Экран у него появляется сам: из этого ответа строится лента уведомлений (п. 1) |
| `GET /services?master_id=<id>` | Экран будем верстать позже | Это фильтр для страницы мастера, которой в прототипе нет (п. 7) |
| `GET /health` | Оставить как есть | Служебная проверка живости, экран ей не нужен |
| `GET /settings` | Оставить как есть | Экраны-потребители есть (лендинг, воронка, `System 01`) — их нужно просто подключить, см. п. 13 |

### Чего на стороне экрана решить нельзя

- **Уведомления:** хранение признака «прочитано», действие «отметить все как
  прочитанные» и счётчик непрочитанных на колокольчике и в сайдбаре (пп. 1, 2).
- **Профиль:** сохранение личных данных, смена пароля, переключатели
  уведомлений, загрузка фото, удаление аккаунта (п. 3). **Решено:** бэкенд ради
  них не открываем, эти блоки из вёрстки убираются — экран `16` верстается
  только с «Активными сессиями». Поле «Дата рождения» убирается в любом случае:
  его нет и в таблице `users`.
- **Восстановление пароля:** экраны `14` и `15` целиком — запрос ссылки и
  установка нового пароля по токену (п. 4).
- **История записей:** выдача больше 100 записей — у `GET /appointments`
  потолок `limit` равен 100, клиентская пагинация дальше него не идёт (п. 5).

## Что добавлено в переходы

Правка от 18.10.2026: клиентские экраны, у которых кнопки и ссылки никуда не
вели, довязаны. Менялась только навигация — разметка, стили и тексты прежние.

Приём выбирался по тому, что уже есть в файле: на страницах с блоком `DCLogic`
(`System 01`) — `onClick="{{ goToBooking }}"`, как в воронке и кабинете; на

экране `12`. Новых скриптов не заводили.

**Сознательно не трогали:**

- `13. Регистрация`, ссылка «обработка персональных данных» — страницы с текстом
  согласия в прототипе нет, вести некуда.

  шаг наступает после письма, а не по клику. Вести кнопку прямо на
  `15. Новый пароль` значило бы нарисовать поток, которого не будет.
- `12. Вход` — экран уже был связан полностью, правок не потребовалось.

Проверено в браузере: все девять переходов открывают нужный файл, кнопки
выглядят как прежде, ошибок в консоли нет.
