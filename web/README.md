# Фронтенд

Здесь два слоя, и они живут рядом:

| Что | Где лежит | Какой адрес |
|---|---|---|
| **Вёрстка** по прототипу и дизайн-системе | `web/pages`, `web/css`, `web/js` | `/` |
| **Черновой тестовый фронт** (им проверяли API руками) | `web/public` | `/draft/` |

Файлы прототипа (`*.dc.html` в корне) не меняются и использованы только как
образец: какие экраны предусмотрены для клиента, мастера, администратора.

## Раздел администратора (`/admin`) — следующая итерация

Каркас: сайдбар с меню «Записи», «Услуги» и «Мастера», шапка и три пустые
страницы — данными они пока не наполняются. Это задача следующей итерации;
клиентская часть к ней уже закрыта целиком. Образец — административные экраны
прототипа (23, 31, 28); какие эндпоинты наполнят каждый раздел, написано на
самих страницах и в [docs/ui-map.md](../docs/ui-map.md).

**Вход один на всех.** Второй формы для администратора нет: все входят через
`/login.html`, а `POST /api/auth/login` возвращает роли (`user.roles`, сервер
собирает их по таблице `user_roles`). Если ролей в ответе почему-то нет,
`js/login.js` спрашивает их отдельно — `GET /auth/me`, — и только потом
выбирает страницу: клиента ведёт в кабинет, администратора — в `/admin`.
Прерванная запись важнее роли: пришли на вход с шага воронки (`?next=…`) —
вернётесь в воронку.

Если администратор всё же оказался в кабинете (вошёл со старой вкладки,
пришёл по закладке), путь в раздел виден там же — пункт «Админ-панель» в
сайдбаре. А кто попал на `/admin` без роли, видит на странице отказа свой
аккаунт и его роли: по ним сразу понятно, почему не пустило.

**Роль проверяется на сервере, а не в интерфейсе.** Рубежа два:

| Что закрыто | Где проверка | Ответ без роли |
|---|---|---|
| `/api/admin/*` | `requireRole('admin','owner')` в начале [api/src/routes/admin.js](../api/src/routes/admin.js) | 403 |
| `/admin` и всё под ним | guard в [web/server.js](server.js) — спрашивает у API `GET /api/auth/me` с cookie запроса | 403 и страница «Этот раздел только для администраторов» |

Без сессии `/admin` уводит на `/login.html`, а не показывает 403: человек не
клиент с чужими правами, он просто не вошёл.

Пункт «Админ-панель» в сайдбаре кабинета лежит в разметке скрытым и
показывается только аккаунту с ролью (`showAdminLink` в
`js/account-shell.js`). Это удобство, а не защита: скрытый пункт меню ничего
не закрывает — закрывают его два рубежа выше.

Роли везде проверяются как **вхождение в список** `user.roles`, а не равенство:
в схеме они хранятся списком (`user_roles`), и у одного человека их может быть
несколько — например мастер, который заодно администрирует. Получить роль из
интерфейса нельзя: её назначают в базе данных, формы выдачи прав в сервисе нет
и не планируется.

## Сессия

Вход и регистрация опираются только на куку, которую ставит сервер:
`HttpOnly`, `SameSite=Lax`. Страницы её не читают и не пишут, `session_token`
из ответа не используется, в `localStorage` и `sessionStorage` не кладётся
ничего. Поэтому все запросы идут с `credentials: 'same-origin'` и через один
origin — это же причина, по которой у фронтенда свой dev-сервер с прокси.

## Чего ещё нет

- **Воронка записи** свёрстана целиком: шаги 1-4, «Запись создана» и
  «время занято». Из неё не хватает только того, чего нет в API: гость не
  может удержать слот (`POST /holds` требует сессию — на шаге 3 об этом
  сказано прямо), а точек «много/мало окон» в клетках календаря нет, потому
  что это был бы запрос доступности на каждый день месяца. Подробности — в
  конце `css/booking-time.css`.
- **Кабинет** свёрстан целиком: экраны 7-11, 16 и 17. Два последних ужаты
  решениями карты экранов, и это видно на самих страницах:
  - **17 «Уведомления»** собраны из `GET /appointments?scope=all` (решение 1):
    ни таблицы уведомлений, ни роутов в API нет. Поэтому на экране нет
    бейджа непрочитанных, фильтра «Непрочитанные» и «Отметить все как
    прочитанные» — признак «прочитано» негде хранить (пп. 1-2 карты). Нет и
    «Пароль изменён»: смены пароля в API тоже нет;
  - **16 «Профиль»** верстался только блоком «Активные сессии» (решение 3).
    Личные данные показаны из `GET /auth/me` на чтение: сохранять их нечем.
    Смены пароля, переключателей уведомлений, загрузки фото, удаления
    аккаунта и поля «Дата рождения» на экране нет;
  - **11 «История»** берёт сто последних записей одним ответом
    (`scope=past&limit=100`), а период, мастера, услугу и страницы считает на
    клиенте (решение 5): других параметров у `GET /appointments` нет. Когда
    записей ровно сто, экран говорит об этом строкой под списком.
  «Да, отменить» на экране 9 по прототипу вело на экран 11; сейчас отмена
  по-прежнему уводит на `account.html?tab=cancelled` — тот же список, в
  котором отменённая запись видна сразу.
- **Восстановление пароля** — экраны `14` и `15` свёрстаны, но не работают:
  в API нет ни запроса ссылки, ни установки пароля по токену, и почты в
  проекте нет вовсе. Поля и кнопки на них выключены, на экране об этом
  сказано. Появится эндпоинт — останется снять `disabled` и добавить
  обработчик отправки.

## Черновой тестовый фронт

Обычные формы, списки и кнопки, минимум стилей. Задача — проверять работу API
руками, а не выглядеть хорошо. Он никуда не делся, просто уступил корень
вёрстке: теперь это `/draft/`, например `/draft/admin.html`.

## Запуск

Две команды в разных окнах:

```bash
npm start
```

```bash
npm run web
```

API поднимется на `http://localhost:3001`, фронтенд — на
`http://localhost:4000`. Для API нужен `.env` и выполненный `npm run seed`.

Порт API искать не нужно: если 3001 занят посторонним сервисом и API
поднялся рядом, `web/server.js` найдёт его сам на 3002–3005 и скажет об этом
в консоли. Задать порты явно можно аргументами — они одинаково работают в
PowerShell, cmd и bash:

```bash
node web/server.js --api-port 3002 --port 4100
```

Переменные `WEB_PORT`, `API_PORT` и `API_HOST` тоже читаются, но запись
`API_PORT=3002 node web/server.js` — это синтаксис bash: в PowerShell она
даёт ошибку «API_PORT=3002 is not recognized», и порт там задаётся отдельной
командой `$env:API_PORT=3002`. Аргументы избавляют от этой разницы.

В Claude Code обе команды заведены в `.claude/launch.json` как конфигурации
`api` и `web`.

## Почему свой сервер, а не просто html-файлы

Сессия живёт в HttpOnly-cookie с `SameSite=Lax`, а CORS в API нет. Со
страницы, открытой с другого порта или как `file://`, браузер не отдал бы
cookie и не дал бы прочитать ответ. Поэтому `web/server.js` отдаёт статику и
проксирует `/api` на API: один origin — и всё работает без правок в API.

Если API не запущен, прокси отвечает `502` с текстом «API не отвечает» —
страница показывает это сообщение, а не висит. А если порт 3001 занят чем-то
посторонним (API тогда поднимается рядом, на 3002), `web/server.js` при старте
предупредит об этом в консоли — укажите порт явно:
`API_PORT=3002 node web/server.js`.

## Страницы чернового фронта

Все адреса — от `/draft/`.

| Файл | Что проверяет |
|---|---|
| `index.html` | `/api/health`, `/api/settings` и правила записи |
| `admin.html` | все записи с фильтрами и постраничным выводом, статусы, услуги, мастера |

Клиентские черновики (`login.html`, `catalog.html`, `availability.html`,
`book.html`, `account.html`) удалены: их заменили свёрстанные экраны в

её верстают следующей.

## Ошибки в черновом фронте

Все ошибки API показываются текстом в блоке сообщений наверху страницы:
статус, код, сообщение и разбор `details` по полям. Отдельно разворачивается
`nearest_slots` — подсказка API при конфликте.

Занятое время (`409`, `details.reason = overlap`) обрабатывается отдельным
сообщением: «Это время уже занято — запись не создана» плюс ближайшие
свободные начала кнопками, которые сразу подставляют время в форму.

## Чего нет в черновом фронте

Кабинет мастера (`/api/master`), клиенты студии (`/api/admin/clients`),
расписание и блокировки мастера правятся только частично: график
показывается как JSON по кнопке «График». Это осознанный объём — в задании
перечислены шесть страниц.
